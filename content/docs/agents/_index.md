## 这一章写给谁

写给不打算手写每一行、而是让编码智能体接手这个仓库的人。前提只有一个：仓库根的 `AGENTS.md` 存在并且是准确的。它是一份给代理读的简报——目录地图、构建命令、不该碰的路径、内容规则——也是唯一需要先读的文件。这一章是对它的展开说明，不是它的替代品。

## 为什么可以靠对话维护

因为判断一页要不要读、改动会牵动什么，靠的不是正文的语气，而是可读的字段。

- 页面的门槛与产出写在 front matter 里：`difficulty`、`estimatedTime`、`prerequisites`、`outcomes`。它们由 `layouts/_partials/facts.html` 渲染成信息面板，同时进入 `/pages.json`，人和代理看到的是同一份答案；
- 章节顺序由 `_index.md` 的 `weight` 决定，页面在章节里的位置由页面自己的 `weight` 决定，所以"插一页、排顺序"是可以被描述和验证的；
- 双语是成对的：`name.md` 是简体中文，`name.en.md` 是英文，同名同目录。任何只改一半的请求都应该被指出来。

结果就是：一句请求——"在部署一章里补一页讲缓存，放在 GitHub Pages 之后"——已经包含足够的信息去定位文件，而不需要先解释整个站点的结构。

## 三条不能商量的约束

1. **产物不是源码。** `public/`、`resources/`、`hugo_stats.json` 和 `.hugo_build.lock` 都是输出或状态，永远不手改。
2. **改动必须能被证明。** 用仓库的严格构建拿到退出码 0，然后读渲染出来的 `public/**` 文件，而不是复述自己刚写的源码。
3. **想展示短代码语法就必须转义**，并且永远不要把 Hugo 的内部占位符粘进内容。这两条不是风格问题，违反其中任何一条都会让整个站点构建失败，而不只是坏掉那一页。

## 本章内容

[用对话维护这个站点](/docs/agents/workflow/) 是操作手册：代理的入口、事实在哪里、怎么验证一次改动、哪些目录不能碰、内容红线的原文，以及一个完整请求从发问到被证明的走法。它还记录了两个受支持的页面开关——正文里的目录短代码和 front matter 里的 `notice` 横幅——省得有人自己去写 HTML。

想先弄清仓库里哪个目录归谁管，读[目录结构](/docs/start/directory-structure/)；想知道这个主题到底实现了哪些特性，读[特性矩阵](/docs/reference/feature-matrix/)。
